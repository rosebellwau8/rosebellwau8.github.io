缘起：好的思考方式被困在静态文本里

前阵子读了数字生命卡兹克那篇分享 12 个常用 Prompt 的文章。文章里提的那些思考方式很打动人，它不教 AI 怎么编造套话，而是帮你理清模糊概念、拆解事实与立场、做正反论证以及设计最小可行实验。它把 AI 当成了"思考外骨骼"。

但现实很残酷：收藏 ≠ 会用。

好的 Prompt 存进收藏夹后，往往就死在了里面。每次遇到问题，光是翻收藏、找文本、复制粘贴、补上下文就足够折磨；换到 Claude 或 Codex 环境还要重新适配。更糟的是，简单问题（比如"Python 3.11 能用吗"）根本不需要庞大的思考框架，直接回答就好。

我不满意的是"好的思考方式被困在了静态文本里"。去市场上看了一圈：

  • Prompt 合集：换汤不换药，全靠人工硬记。
  • 重型 Agent 框架：动辄搞引擎、数据库、复杂工作流，太笨重。
  • 特定平台 Skill：强绑定某种环境，缺乏通用性。

我想要的不是第 13 个 Prompt，而是一个机制：思考方法在需要时自动触发、不需要时悄然隐退、跨平台通用，且步骤间能传递结构化数据。

这就是开源项目 Thinking Protocols 的由来。

核心架构：Protocol、Artifact 与 Adapter

为了解决 Prompt 难以工程化和标准化的问题，我拆出了三个核心概念：

+-------------------------------------------------------------+
|                      Protocol (协议)                         |
|  - 机器读: YAML 元数据 (触发条件/输入输出/边界)                  |
|  - 人类读: Markdown 思考流程                                  |
+-------------------------------------------------------------+
                              │
                              ▼
+-------------------------------------------------------------+
|                     Artifact (交付物)                        |
|  - 结构化 JSON (如 verified_claims.v1, decision_memo.v1)     |
|  - 作为 API 接口在不同 Protocol 间无缝流通                      |
+-------------------------------------------------------------+
                              │
                              ▼
+-------------------------------------------------------------+
|                     Adapter (平台编译)                      |
|  - 保持语义与边界完全一致                                      |
|  - 编译输出为 Generic Markdown / Codex Skill 等不同格式       |
+-------------------------------------------------------------+

Protocol（协议）

不要把 Prompt 看作给 AI 演戏的咒语，真正有价值的是思考规则。 Protocol 是单事实源文件（protocols/<id>/PROTOCOL.md），头部是机器可读的 YAML 元数据（明确输入、输出、阶段、能力要求与终止条件），尾部是人类可读的 Markdown 过程。

区别：Prompt 关注"一句话怎么写"，Protocol 关注"一次认知工作如何可靠发生"。

Artifact（结构化交付物）

传统的 Agent 流水线直接把上一句的自然语言长文本丢给下一步，极其脆弱且难以预测。

Thinking Protocols 引入了 Artifact，要求每个思考阶段必须产出强类型的结构化数据（如澄清问题的 clarified_problem.v1、事实核查的 verified_claims.v1）。不同 Protocol 之间不看对方的推导过程，只通过标准 API（Artifact）交换数据。

比如：先用 steelman-both-sides 做出决策备忘录，直接把产出的 decision_memo.v1 喂给 minimum-experiment 自动设计一个 14 天的小试验。

Conservative Router（保守调度器）

很多 Agent 恨不得用户问什么都开个十人圆桌会议。Thinking Protocols 的 Router 极度保守：

  • 用户指定了 Protocol 就严格照办；
  • 简单问题直接回答，绝不过度卷入；
  • 只有确实需要时，才匹配能产出对应 Artifact 的最小 Protocol；
  • 缺乏联网能力（如缺少 web.search）时直接阻断并告知用户，绝不拿着模型记忆冒充实时检索；
  • 设置 routing_priority 优先级，但优先级决不能越过用户指令和安全边界。

Adapter（跨平台适配器）

为了防止同一个方法在不同平台演化出不同版本（代码漂移），Adapter 充当了"编译器"的角色。

  • 允许改变文件名、语法包装和工具绑定方式；
  • 严禁修改语义：阶段顺序、停止条件、安全边界必须百分百一致。通过 Conformance 校验和摘要比对，一旦发现偷偷改动语义直接报错阻断。

从 4 个试点走到 12 个协议

v0.1.0 先落地 4 个协议（socratic-questioning、fact-checking、steelman-both-sides、minimum-experiment）证明了骨架能跑起来，但它们还只是代表性试点。真正的难题不是把清单填满，而是把另外 8 种常见、又容易被滥用的思考方式，逐个翻译成同一份合同：它们什么时候介入，依赖什么证据，最多走几步，什么时候必须停。

v0.2.0 没有把 8 段 Prompt 原文搬进来，而是根据公开描述的方法、目标和边界独立重写。现在 12 个协议都各自住在 protocols/<id>/PROTOCOL.md，有自己的 examples 和 evals；Registry、Generic 输出和 Codex Skill 都从这些单一真源生成。目录变长了，语义反而更收敛。

Protocol它解决什么问题边界
socratic-questioning把模糊、带假设的问题问清楚最多 6 轮，缺乏新信息就停
fact-checking核验可外部检查的主张区分事实、推断、立场；没有证据能力就阻断
steelman-both-sides为至少两个可信选项建立最强论证不制造机械对称，也不替用户拍板
minimum-experiment把不确定性变成低成本、可逆的小试验必须有假设、指标、预算和止损线
dual-layer-explanation同一主题同时给直观层与机制层解释两层事实一致，不用错误类比换易懂
reverse-engineering从结果倒推组成、约束、机制和重建路径默认 bounded workflow；外部对象按需取证
horizontal-vertical-analysis沿时间纵轴和当下横截面做研究需要 research intent；记录 cutoff、来源和冲突
expert-panel让多个分析视角围绕同一证据真正分歧角色不是虚构专家，不能替代现实证据
first-principles拆掉未经验证的惯例，从约束和目标重新推导不确定的基础事实必须标注假设或取证
cross-domain-transfer寻找可迁移的机制，而不是漂亮的表面类比要检验结构相似、边界和失效条件
talent-discovery从真实行为中形成待验证的能力兴趣假设允许跳过敏感问题，不做诊断，默认不持久化
life-design把现实约束转成可执行的人生设计实验不生成终身标签，不替代医疗、法律或财务意见

其中最容易被误解的是自我探索和研究这两组。自我探索不是给人贴标签，研究协议也不是让模型凭记忆写一篇“看起来很完整”的报告。talent-discovery 和 life-design 都把结论写成现实待验证的假设，允许跳过敏感问题，并设置最大问题数和 early stop；horizontal-vertical-analysis 与 cross-domain-transfer 则把证据日期、来源适用范围、冲突处理和迁移失效条件写进流程。这样做有点不浪漫，却能防止思考工具越聪明，越替人胡编。

细节决定可靠性

  • 跨平台一致性：对文件执行 LF 换行归一化，解决 Windows 与 Linux 摘要算法不一致的问题。
  • 严苛测试：不仅测试正确的 Artifact 样例，还专门针对缺少字段、类型错误、证据冲突、缺少必需 capability、consent gate 和误触发编写拒收测试。全库最终达到 110 个测试通过、90.59% 的覆盖率。
  • 最小扩展：12 个协议仍复用原有 7 个 Artifact，没有为了“看起来正式”而制造敏感持久化数据。新增协议的最终结果如果没有后续消费者，就明确声明为 terminal output。
  • 行为一致：Router 仍然优先 direct answer，默认最多一个主 Protocol；普通解释不会因为多了 dual-layer-explanation 就被强行升级，研究协议没有 research intent 不会自动启动，talent-discovery 和 life-design 没有同意不会自动运行。

快速上手与开源信息

项目采用 Apache-2.0 协议开源，未直接复制原文章或 Prompt 原文，仅保留相关元数据与重写抽象。

代码仓库：rosebellwau8/thinking-protocols

Release 发布：v0.2.0 Releases

直接使用

不用跑代码，进入 dist/ 目录即可：

  • 通用 Markdown：直接复制 dist/generic/ 目录下的 .md 文件，作为 System Prompt 发给任意大模型即可使用。
  • Codex：将 dist/codex/skills/ 下的文件夹放入 Codex 的 skills 目录即可完成注册。

开发者调试与扩展

# 克隆与环境配置
git clone https://github.com/rosebellwau8/thinking-protocols.git
cd thinking-protocols
python -m venv .venv

# 激活环境 (Windows: .venv\Scripts\Activate.ps1 | Linux/macOS: source .venv/bin/activate)
pip install -e '.[dev]'

# 校验与构建
thinking-protocols validate
thinking-protocols build-registry
thinking-protocols build --adapter generic
thinking-protocols build --adapter codex
pytest

编写自定义 Protocol 时，请遵循先写测试用例（evals.yaml），再写实现的顺序。先写反例，才能逼自己厘清这个思考工具"什么时候不该出现"。

总结

真正的认知系统，重点不在于多频繁地发表意见，而在于知道何时介入、何时止步、何时承认无能为力，以及何时把控制权还给人类。

从 v0.1.0 的 4 个代表性试点，到现在完整的 12-Protocol library，变化并不在于“AI 会想更多”，而在于每一种思考方式都知道自己的入口、证据、产物和出口。它们可以被调用，也可以被拒绝；可以跨平台生成，也必须接受同一套 conformance 检查。

我越来越觉得，好的认知工具不是替人做决定的机器，而是一组边界清楚、知道何时介入又知道何时退后的协议。Prompt 终于不再只是收藏夹里的文字，而成了可以被验证、被复用、也可以被人随时关掉的工程。
