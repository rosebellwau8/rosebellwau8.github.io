我让 AI 把脚本里的规矩抽成了 Skill，第二天坑全回来了

jogtor 2026 年 8 月 2 日 08:41

把踩坑踩出来的铁律从代码里抽出去，换成一份「建议书」——听起来很优雅，但火车从来不看路标。

01事情是这样的

我维护一个数据抓取脚本，跑了快半年。脚本本身不复杂——调接口、解析 JSON、入库，几百行。但它身上绑了十几条不成文的"规矩"，全是踩坑踩出来的。

举两条你最可能也踩过的。

第一条：某数据源的关键字段偶尔返回空值（null）。脚本必须跳过这条记录，不能写默认值 0 进数据库。一旦 0 混进去，下游做数据分析的时候 0 被当成真实数值参与运算，一整批报表直接报废。而且这种错误当时发现不了——数据跑完了、入库了、一切正常。月底对账才看到偏差，已经没法重跑了。

第二条：数据源分页返回。接口一次只给 50 条，总页数在响应头里。你必须在脚本里循环把所有页取完再落盘。只取第一页？表面上看数据正常入库了，实际上少了七成记录。同样是月底才发现。

类似的东西还有十几条：时间戳必须统一转为 UTC 再存、某接口偶尔返回负数必须丢弃、特殊分类 ID 段要用另一套解析逻辑……每一条都是某次事故后加上去的，用 if 判断、while 循环、assert 断言，硬编码在脚本里。丑是真的丑，但修好之后没再出过事。

02翻车

昨天抓数据时动了一个念头。

这些规矩，有些看起来挺"通用"的——比如说"遇到空字段就跳过"，这难道不是每个合格的程序员都会做的吗？为什么要像防贼一样写在代码里？

我想：是不是可以把这些规矩抽出来，写成 AI agent 的 skill（技能文件）？脚本只保留核心逻辑，规矩作为外挂指导，agent 帮我维护时自然就会遵守。代码瘦了，改起来也省心，不用每次在几百行里翻对应的 if。

我把这个想法丢给 agent。它非常笃定：完全可以。把硬编码规则抽成 skill，脚本会清爽不少，以后维护也更灵活。

我信了它的邪。

它帮我重构了脚本。删掉了那些 if 判空、while 分页、assert 校验，生成了一个 skill 文件，里面列出了所有规矩，每条都写得很清楚。代码肉眼可见地瘦了，少了快四十行，我还挺满意。

今天早上跑完数据，打开数据库一看，血压直接上来：空字段全部写成了 0，整整齐齐。分页只拉了第一页，少了四成多数据。时间戳还是原来的混搭时区，UTC 没统一。三条最硬的规矩，一条没守。

我打开 skill 文件再看了一遍——规则写得明明白白，没有任何歧义。但 agent 在抓数据的时候，就是没执行。

那一刻的心情不是愤怒，是一种"我刚才到底在想什么"的恍惚。我亲手把铁轨拆了，换成了路标，然后期待着火车能自己认识路……

03为什么会这样

冷静下来想，道理很简单。三句话就能说清。

脚本是确定性执行。if 判断走到那行一定会求值，while 循环一定会转。代码没有"今天状态不好"，没有"我觉得这次可能不需要"。铁轨铺好，火车只能沿着走。

Skill 是概率性指导。它是一段文本，放在上下文窗口（context window）里，等着 agent 读到它、理解它、然后决定执行它。问题就出在这三个"等着"上。

第一，agent 不一定读到

上下文窗口有长度限制。你的 skill 文件排在十几个文件、几千行代码的后面，注意力分配（attention）走到那里已经衰减。换个新会话，skill 可能因为加载策略不同而压根没出现。

第二，读到了不一定理解对

"空字段必须跳过"——agent 很可能理解成"空字段给一个合理默认值"，因为在海量训练数据里，大多数场景确实该填默认值。你的特殊规矩恰好和通用经验相反。

第三，理解了不一定执行

agent 生成代码时面对的是全景上下文——你的 prompt、项目结构、报错信息、上一条对话、系统指令。你的 skill 只是众多信号之一。其他信号更强的时候，它被淹没，完全正常。

这三层不确定性叠加在一起，等于你把"绝对不能出错"的事交给了一个每次都可能重新理解一遍的东西。

脚本是铁轨，skill 是路标。火车不看路标。 再说一遍：这不是 skill 的 bug。Skill 的设计目标是"提高 agent 输出质量的概率"，不是"确保某条规则被无条件执行"。它是建议，是倾向，是"在其他条件允许且你恰好记得的前提下最好这样做"。把铁轨的活交给路标去干，翻车了不是路标的问题，是我的判断问题。

04那到底什么该放哪？

翻车之后我整理了一个判断框架。现在每次想把一条规则从脚本里往外抽，先拿这张表过一遍。你也可以用它审视自己项目里散布在脚本、prompt、skill 文件、README 里那些不成文的规矩。

铁轨 · 入脚本（硬编码） 路标 · 入 Skill（软指导）
判断维度 入脚本（硬编码） 入 Skill（软指导）
违反了会怎样数据损坏、结果错误、不可逆风格不佳、效率略低、可事后修复
是否需要每次无条件执行是，没有例外否，可随场景灵活调整
能否用 assert / 校验自动检测能，一行断言就能卡住不能，需人工判断好坏
执行者是谁代码 / 脚本自己跑AI agent 辅助生成或修改代码
是否依赖运行时上下文不依赖，规则固定不变依赖，需理解当前场景再决定
违反后多久能发现很久以后才对账发现（最危险）当场或很快就能看出来
用法很简单：一条规矩，六个维度逐行对。只要有一个维度落在左列——"数据损坏""必须执行""能写断言""不依赖上下文""很久才发现"——别纠结，写进脚本。
「空字段跳过」→ 必须进脚本 违反导致数据损坏 ✓、每次必须执行 ✓、能写 assert ✓、不依赖上下文 ✓、月底才发现 ✓。六条全在左列，必须进脚本。
「变量命名用驼峰」→ 适合放 Skill 违反不坏数据 ✓、不需要强制 ✓、写不了断言 ✓、agent 写代码时顺手遵守就行 ✓。这是 skill 该干的活。

如果你遇到一条规矩在左列和右列各中几个，比如"违反后数据会错但能自动修复"，先看第一个维度——违反后果的严重性。后果不可逆，其他全免谈。

05后来我怎么做的

我把删掉的三十多行代码一条一条加回去了。if、while、assert，原样恢复。丑就丑吧。小半年没出过事的东西，不需要变漂亮。

Skill 里只留了真正适合它的东西：代码风格偏好、注释用中文还是英文、文件命名是蛇形还是驼峰、"生成测试优先用 pytest 而非 unittest"——这类"做对了加分，做错了不致命"的柔性指导。

数据正确性不是风格问题。它不是加分项，是及格线。

能让代码强制执行的，绝不让 agent 自觉遵守。

agent 是非常好的同事。但你不能把数据库约束写在同事的便签纸上，然后期待它永远不会被风吹走。
