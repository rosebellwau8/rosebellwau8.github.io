GitHub 对非程序员来说，核心价值就两点：云端备份和版本回退。不需要懂 Git 原理，不需要会写代码，会按步骤操作就够了。

GitHub 到底是什么

搜 GitHub 出来的解释常常是「分布式版本控制系统」这类词，看着头大。简单理解成两样东西就行：

  • 云端保险箱：本地写的东西推上去后，云端有一份完整备份。硬盘坏了、电脑丢了、被咖啡泼了都不怕，登录 GitHub 网站项目还在。
  • 时光机：每次提交，GitHub 都存一个快照，像游戏存档点，随时可以读档回到任意时间点。改炸了回到上个版本，上周能跑这周不行就回到上周。

分支管理、代码审查、Pull Request 那些是程序员团队协作才需要的，个人使用不需要管。

选工具：从 GitHub Desktop 开始

强烈建议非程序员从 GitHub Desktop 开始。去 desktop.github.com 下载安装，用 GitHub 账号登录即可。

创建仓库并发布

仓库可以理解为项目文件夹在 GitHub 上的镜像：

  1. File → New Repository；
  2. Name 填项目名（示例 hospital-tools），Local Path 选项目所在文件夹；
  3. 点 Create Repository；
  4. 左下角 Summary 写「首次提交」，点 Commit to main；
  5. 右上角 Publish Repository → Publish。

整个过程不超过两分钟。它只是把文件复制一份到云端，不会动你本地的文件，可以放心操作。

命令行方式（进阶）

如果以后想进阶，或有些操作 Desktop 做不了，可以试命令行：

# 进入项目目录
cd C:\Users\Administrator\hospital-tools
git init
git add .
git commit -m "first commit"
git branch -M main
git remote add origin https://github.com/你的用户名/hospital-tools.git
git push -u origin main

第一次 push 会弹浏览器授权，同意即可。命令就固定的这几条，多试几次就熟了。

日常三板斧：pull / add+commit / push

  • 开工前 git pull：把云端最新版本拉到本地。
  • 干完活 git add . 加 git commit：add 是把改动加入暂存，commit 是存档并写一句说明。
  • 然后 git push：把存档推到云端。

GitHub Desktop 上更简单：打开软件，Fetch origin 看云端有无更新，有就 Pull；改完写 Summary，Commit，再 Push origin。全程不用敲命令。

铁律：先拉后推。 每次开始干活前先 pull，不管觉得有没有必要。忘了 pull 直接改、改完一 push，大概率会冲突。

换新电脑：clone

新电脑第一次用，把项目拉下来即可：

git clone https://github.com/你的用户名/hospital-tools.git

之后仍是先 pull 后 push 那一套。多台电脑轮流干活时，只要每次开工前 pull、干完 push，各处的项目永远是最新的。

commit message 怎么写

别写「修改」「更新」「aaaa」「test」这类记录，三天后你根本不知道改了啥。规则很简单：动词开头，说清改了什么。例如：

  • fix: 修复病历导出乱码
  • add: 新增质控模块
  • update: 更新数据库配置

花十秒钟写清楚，能省大量排查时间。

六个常见坑

坑 1：多设备同步冲突

最容易出现。现象：电脑 A 改了 config.py 忘了 push，电脑 B 也改了 config.py 并 push，回到 A 一 pull 报错 CONFLICT，文件里出现一堆 <<<<<<< 和 >>>>>>> 标记。

原因是两台机器改了同一区域，Git 不知保留谁。处理：打开冲突文件，会看到这样的结构：

<<<<<<< HEAD
你在这台电脑上改的内容
=======
云端上的内容
>>>>>>> origin/main

手动选择保留哪段、删掉不要的，再把所有标记删干净。然后：

git add config.py
git commit -m "resolve: 合并冲突"
git push

预防只有一条：每台设备开工前先 pull，冲突率能降到接近零。

坑 2：提交了大文件或敏感文件

git add . 后直接 push，可能遇到两类问题：

  • 大文件：单个文件超过 GitHub 的 100MB 限制会报错（如 data.db 这类数据库文件）。
  • 敏感文件：.env 里常存数据库密码和 API 密钥，一旦推到公开仓库就等于泄露。

还没 push：撤回很简单，git reset --soft HEAD~1 会撤销最近一次提交，但文件改动都还在。把不该提交的文件删掉、配好 .gitignore、重新提交即可。

已经 push 了敏感文件：三步走——① 立刻把仓库改为 private；② 马上更换泄露的密码和密钥，就当已经泄露；③ 配好 .gitignore 后重新提交。别存侥幸心理，网上爬虫比想象中快。

坑 3：.gitignore 配晚了

.gitignore 是忽略清单，告诉 Git 哪些文件不管。若首次 commit 前忘了配，像 node_modules 这种几百 MB 的文件夹就进了仓库，之后每次 clone、push 都慢。

先创建 .gitignore，写上：

node_modules/
*.db
.env
__pycache__/

再把已追踪的文件从 Git 移除（只移除追踪，不删本地文件）：

git rm -r --cached node_modules
git add .gitignore
git commit -m "chore: 添加gitignore"
git push

--cached 很关键：只从 Git 追踪列表移除，不删你本地文件。

坑 4：改了一堆不知道改了啥

改了一下午想提交，却记不清动了哪些文件。直接 git add . 又怕把半成品一起提交。

提交前先看一眼：

git status
git diff

status 列出改了/新增/删除了哪些文件；diff 逐行显示具体改动。GitHub Desktop 里点文件名就能看对比，更直观。建议每次 commit 前都看一眼，多花十秒少出一堆问题。

坑 5：想撤销但不会

撤销方式取决于你做到哪一步：

  • 已 commit 未 push，想撤销但保留改动：
  • 已 push：不能简单撤销，因为别人可能已拉取。安全做法是生成反向修改来抵消：
  • 想回到某个历史版本：先看历史：
git reset --soft HEAD~1

—— 撤销最近一次提交但保留文件改动。

git revert HEAD
git push

revert 不删历史，新增一条「反向提交」，历史完整，不会搞乱别人代码。

git log --oneline -5

找到目标版本 commit ID，再：

git reset --hard a1b2c3d
git push --force

注意：--hard 会丢掉该版本之后的所有改动，--force 会强制覆盖远程历史，非常危险，仅限个人仓库使用，团队项目绝对不要这么做。

坑 6：token 过期或认证失败

某天 push 突然报 Support for password authentication was removed 或 403 Forbidden，不是账号出问题——GitHub 从 2021 年起不再接受密码认证，必须用 Personal Access Token（PAT）代替密码，且 token 会过期。

处理：GitHub 头像 → Settings → Developer settings → Personal access tokens → Generate new token，权限勾选 repo，生成后复制那串 token，push 时粘贴它而不是密码。

Windows 上若旧 token 缓存导致认证失败：控制面板 → 凭据管理器 → Windows 凭据，找到 git:https://github.com 那条删掉，下次 push 重新输入新 token。token 有效期可直接设为 No expiration（对非程序员够用，只是安全性略低）。

最后那条最重要：遇到没见过的报错，先 git status 看状态，再搜报错信息。绝大多数情况 status 就能告诉你答案，剩下复制报错去搜，基本都有人遇到过。

写在最后

版本控制不该是程序员的专利。写论文改了二十稿、做 PPT 不如早上版本、两人同时改方案对不上——这些场景 GitHub 都能解决。它不只是云同步，更是给工作装了一台「时光机」：每次提交都是存档点，可回到任意时间点。

你不需要是程序员，不需要懂 Git 原理，花两个小时跟这篇走一遍，就能给自己的工作上一个保险。两个小时换一份「再也不怕丢东西」的底气，很划算。
